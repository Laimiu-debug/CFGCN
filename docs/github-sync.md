## 执行位置与频率

- 沿用现有每小时心跳 `cfgcn`，不另建定时器；每次巡检收尾检查可提交增量。
- 仓库固定为 `G:/CODE/CFGCN`，远端必须核对为 `Laimiu-debug/CFGCN`。
- 当前同步分支为 `feat/xiyou-rust-prototype`，推送至同名 `origin` 分支。当前仓库、分支或上游变化时先核实原因，不自动切换他人工作的分支。
- 没有新增且可提交的内容时不制造空提交。

## 提交内容与验核

1. 先读项目约定、调度清单及负责人回执，从已完成并冻结的源码、必要配置、说明与来源/SHA清单组成明确批次。多位负责人仍在写的半批内容继续留在工作区，下一轮接续。
2. 代码按受影响范围使用已有的规则、导入/编译、组件或自然流程证据；文档修改检查差异、格式与事实即可。不因定时同步重跑固定压力矩阵，也不等待整款游戏完成才保存已验证增量。
3. 使用明确文件清单，记录提交前SHA与验核依据；提交前后若选中文件被另一任务改变，重新核对该文件，不覆盖正在推进的工作。保持其他人的暂存区和未提交改动。
4. 排除凭据、令牌、私钥、DPAPI管理包、私人反馈、玩家存档和个人设置；排除 `.local/`、缓存、导入缓存、可重建构建、临时下载与日志。不得以推送要求扩大为上传这些资料。
5. GitHub提交以源码、必要小型资源和交接记录为主。大体积原件、Blender源、运行资源、Windows包和原声录像仍按项目G盘来源/发行交接管理；既有可用的大文件方案按实际核对使用，未有方案的超大文件单列待处理，不塞进普通Git提交。GitHub同步记录不冒称整套资产备份或客户端下载发布。

## 推送与协作

- 提交前确认没有合并/变基冲突或他人的Git写锁；不删除他人的锁文件。
- 使用项目现有提交身份与签名配置；每个提交只含该批明确文件。
- 推送前核对远端分支进度。远端发生变化时先保留本地工作并核对双方提交；不自动stash/reset、重写他人提交或强制推送。
- 推送后用远端实际HEAD核对本次提交，记录提交链接、分支、文件清单、未包含项及必要验核依据。
- 提交/推送故障只处理本步骤并留证，不中断游戏制作、其他聊天或现有服务。通过原本已授权的认证方式执行，不把任何认证正文写入聊天、日志、Notion或仓库。
- 进度和结果复用Notion现有进度页并回读。有实质批次、故障或需用户处理才通知；例行无变化保持安静。

本条授权只包含仓库提交与推送。游戏默认启动/完整流程、Windows包、官网发布及公网验收仍按各自负责人和既有授权分别执行；推送成功不计游戏完成或生产上线。
